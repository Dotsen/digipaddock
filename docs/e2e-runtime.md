# Prepared end-to-end runtime

`e2e-testing` is knowledge; `e2e.request` is the separate developer capability that permits the fixed executor. The developer's sandbox still has no local binding or general network access. A worker has no executor channel and must report that limitation.

## Trusted preparation

Deployment prepares `/var/lib/digipaddock/e2e/runtime` as a root-owned tree with no group/other write bits. It is not assembled from an agent's live worktree by a request. Include:

- `revision.json`: exactly `{"commit":"<full observed 40-character SHA>"}` of the application being tested.
- `app/`: the trusted revision's sources, prebuilt cabinet `dist/`, locked/prepared web `node_modules`, and an existing empty `tmp/` mount point. The executor does not run package managers or build scripts.
- `python/`: a prepared Linux Python environment with the dev cabinet dependencies; `bin/python` must resolve within the bundle or the fixed read-only system mounts.
- `browsers/`: the Chromium binaries matching the pinned Playwright release. Chromium's sandbox must work; there is no `--no-sandbox` fallback.

The trusted source includes `common/cabinet/web/e2e/hosts` (only `127.0.0.1 localhost`) and `nsswitch.conf` (`hosts: files`). The namespace binds these bundle files as its name-resolution configuration. It never imports the host's hosts, resolver or DNS configuration. This keeps the WebAuthn test origin `http://localhost:8765` usable without external name resolution.

`common/install/e2e_runtime_setup.sh install` assembles exactly this from the deployed release: the release tree, the cabinet web built by the base user (`npm ci --ignore-scripts`, `npm run build`; package code never runs as root), a copy of the cabinet's venv, Chromium of the locked Playwright (downloaded once per Playwright version) and the release's full commit. It builds beside the runtime, checks the result by the executor's own rules and swaps it in whole. `check` exits 1 when the runtime is not the deployed release's (stale). The first install is by hand; after that the release service rebuilds the runtime after every release on a host that has one, and its health check reports a stale runtime as a failed `e2e_runtime` check. The factory's component `e2e-runtime` (`install`, `check`) runs the same script under a signed plan.

Provisioning these dependencies and installing the new generated agent policy use the normal approved deployment process. Missing preparation is `blocked`, not a passed test or permission to download dependencies. Only this concrete runtime is needed, not the entire KD-211 backlog.

## Execution boundary

`kd-e2e list` names the fixed `cabinet-smoke` suite — one test of two steps: the owner's sign-in at three widths with a new passkey and a card, then the council of a brief end to end — the owner puts two critics on a card, the analyst hands its brief in, both critics read it (the test cabinet's scripted host plays them), the council's block says it is clean and the owner starts the work. `kd-e2e run cabinet-smoke --card KD-n` accepts no URL, shell, path, test filter, configuration or launch flags. The base executor verifies its channel caller, capability and the approved card's sole assignee.

The executor runs bubblewrap with fresh user, PID, network and other namespaces, a cleared environment, no capabilities and only read-only system libraries and the prepared runtime mounted. A seccomp filter (`kd.e2e_seccomp`, loaded by bubblewrap from a pipe) answers EPERM to the kernel's administrative and rarely needed interfaces — the keyring, `bpf`, `perf_event_open`, `userfaultfd`, `io_uring`, modules, kexec, reboot, swap, clock setting, file handles — and to any call of another ABI (i386, x32); namespaces stay allowed, so Chromium's own sandbox still starts. A host of an architecture without a table (x86_64 and aarch64 have one) reports the runtime unavailable instead of running unfiltered. Only a new private temporary directory is writable as the app's `tmp/`; no host home, production databases, board socket or secrets directory is mounted. The local dev cabinet and browser share this namespace and can reach loopback only. The fixed suite also aborts requests to any other origin.

Limits: 180 seconds wall/CPU time, 512 open files per process, 32 MiB per file. The whole call — bubblewrap, node, Chromium, the cabinet under test and the pages of their in-memory `/tmp` and `/dev/shm` — runs in its own capability-call unit (one instance per connection) with `MemoryMax=3G`, no swap and `TasksMax=1024`: a run past them is killed and reported as failed, never passed, and the host's memory stays the host's. `Popen` applies an inherited Linux `RLIMIT_NPROC` ceiling of 512 **only in the new executor child**. Other existing services retain their own limits. The kernel counts all threads of the child's real UID when deciding whether that child may fork, so this is not a per-run process count. Exhaustion can refuse a run and never means passed. Timeout kills the process group; the PID namespace and parent-death handling end descendants. The temporary database, cookies and synthetic login codes are removed on success or failure. Concurrent requests use separate run directories and network namespaces, so ports and data do not collide. The suite checks login, a synthetic passkey, creating/opening a card, representative widths 360/900/1440, and the council of a brief from the hand-in to the owner's start.

The session host pins the release it started from (`HOST` in the release base), so retention never removes the paths it reads. When a release changes the host's code, `kd-release` asks the factory for the `session-host restart` component step; it runs once active turns have finished and reloads the current worker slot/pack paths. Until then the health check reports `session_host_code` as passed only while that restart is queued.

Only outcome, app commit and artifact metadata reach the card. Failure traces, screenshots and the executor log are retained under a generated private artifact ID, mode 0700, in the base user's own `/var/lib/digipaddock/e2e/runs` (made by the runtime install): at most 50 files and 64 MiB per run, and only the newest 10 runs. The executor reads its log back from the handle it wrote, never by path, since the run folder was the namespace's writable `tmp/`. The retained files may contain synthetic credentials and have no arbitrary agent download/publication API. Review and export through an authorized owner workflow. Runtime preparation and the real namespace/browser probe remain required deployment evidence; loader/unit tests alone do not satisfy that probe.
