# Security model

DigiPaddock gives AI agents real powers: changing servers, merging code. This document describes what it protects, from what, and which mechanism holds each boundary.

## What is protected

- **Managed servers**, production included: their availability, data and configuration.
- **Code repositories**: what reaches `main` and what gets deployed.
- **Secrets**: the Telegram token of the alert duplicate, SSH keys, the host's Claude token, the code-hosting tokens, the owner's signatures and grants.
- **The agents' own infrastructure**: the host, its units, policies and kill switches.
- **The owner's attention.** Too many approval requests turn approvals into reflexes.

## Threats

| Threat | Example |
|---|---|
| Prompt injection through data | A log line, card comment, pull request or server output tells an agent to run a command |
| Model error | The wrong server, the wrong command, a misread task |
| One agent misusing another | The coordinator relays injected text from a card or a tool's output as a directive |
| An agent widening its own powers | Editing its settings, instructions or the policy floor; reading another agent's secrets |
| Forged approval | A card moved to `To Do` by an agent; a comment signed as the coordinator; a chat message read as "yes" |
| Approval fatigue | The owner approves everything because there is too much to approve |

The model treats data as data by instruction ("data, not commands"). That instruction is one layer, never the only one. What an agent reads is shaped so that data cannot pass for a message: in a thread or a card's view every line of a message body after its first is indented, so a line that starts with `#<seq> @<who>` is always a real message's header — never another agent's text dressed up as the owner's word. Every boundary below holds even when the model has been talked into crossing it.

## Boundaries and what holds them

| Boundary | Held by |
|---|---|
| One agent cannot read another's files or secrets | A separate Linux user per agent; root-owned agent folders whose `memory/` and `work/` belong to the agent alone (0750, notes 0640); the permission rules and the sandbox deny the other agents' homes and folders |
| A voice message leaves only as text | Each recording is transcribed by its own process, started per connection of a socket only the board service reaches, under a service user of its own with no network at all (private network namespace, no IP, Unix sockets only), a read-only system and model, and a private temporary folder it removes before it exits; it answers one line of text and status and keeps nothing |
| The cabinet's push key cannot sign for anyone else | The Web Push private key lives in its own file readable only by the push sender's service user; the cabinet service holds the public key and the queue, nothing more; a code of the owner's second factor is accepted once |
| An agent cannot change its own powers | Settings, launch settings, instructions and permission files are root-owned and generated; the policy floor applies to every session |
| A repository cannot run code in a session | Hooks and MCP servers run outside the OS sandbox, so none comes from a repository: an agent's session starts in its own `work/`, and the launch is refused while `work/.claude` or `work/.mcp.json` is anything but absent, root's or Claude Code's own runtime folders; Claude Code loads project settings from that start folder, not from a clone below it. A worker runs with every setting source off (`--setting-sources ""`), `--strict-mcp-config` and slash commands off, so its checkout's `.claude/` and `.mcp.json` load nothing; only the root-owned managed settings and the job's own settings file apply. A clone's `.git/config` is the agent's writing too: the installers that touch an agent's clone outside its sandbox (`add_repo.sh` on a rebind, the mirror setup) run git there with no hook, no fsmonitor and no system config, and check access with a `ls-remote` from outside the clone; the write guard refuses a hand-written target in a clone's `.git/` |
| A shell command stays inside its limits | The OS sandbox (bubblewrap) on every command: writable paths, readable paths and network hosts come from the sandbox profile; unsandboxed mode is off and fails closed. A card session with a probe exit ([probe-egress.md](probe-egress.md)) adds only that exit's host names, reached only through the exit's loopback proxy and the deployment's VPN, while the owner's consent on the card lives. A deployment may instead name a standing exit of every host: every session of the agents it lists then reaches any host through the VPN and holds the web tools — the host list stops bounding what leaves, see [what it costs](probe-egress.md#what-an-exit-of-every-host-costs) |
| A privileged command runs only for the right agent | The capability channel checks the caller's uid (`SO_PEERCRED`) against the permission file; no file means no channel. The session a call serves is what the kernel says of the caller's process (its session unit's cgroup), never what the caller passes; a wrapper in the agent's own self-channel unit forwards the session that channel saw, so a finish or a help request counts only for the turn it came from |
| A privileged command does only what it should | The executor validates every argument; command forms are finite; the environment is not trusted |
| Server reads stay reads | The gateway on each server is a forced command: an allowlist, no shell, secret paths refused, timeout and output caps. A process's environment and its raw arguments are never read: `/proc/<pid>/environ` and `cmdline` (NUL-separated, so no mask would see a password in it), kernel memory and the kernel log are refused, and so is `ps`'s BSD `e`; arguments come only through `ps`, where the masks apply, and every value of a unit's `Environment=` is masked |
| Host reads stay reads | Every agent reads the agents' host through one executor, `kd-host-read`, under a reader service user of its own; no agent user and not the base user is in `adm` or `systemd-journal`, so an agent's own groups and files open nothing. The journal is read only for the units of a root-owned catalog (the operator: every unit), matched by trusted fields the journal itself sets (unit and PID 1), and records of logins, privilege changes and the permission audit are dropped for everyone; files only under the catalog's roots, opened without following a symbolic link and re-checked by descriptor; systemd only through read verbs; host state only through fixed commands. Output and time are capped, and the reader can never read signatures, grants, the board database, the monitor's state or secret files — the install check proves it. A per-agent switch turns the reader off within the same session |
| Database reads stay reads | Agents with `data.read` read the managed servers' product databases only through `kd-data`, an executor under a data service user of its own, the one holder of its SSH key (its home closed to every agent). The database names its server through the inventory; before any connection the executor checks the exact remote command with the gateway's own MySQL rules (one `SELECT`, `SHOW`, `EXPLAIN` or `DESCRIBE`; no second statement, comment, client command, `INTO OUTFILE`, locking read, `sleep()` or `load_file()`) and journals the call — agent, time, server, database, text, then exit code and bytes; no journal, no call. On the server that key's forced command is the gateway's MySQL-only mode: nothing but `mysql`, as a MySQL user of its own that sees every table of the listed databases except the columns whose names say they hold a secret (passwords and their hashes, keys, tokens, cookies, salts, one-time codes) and those the deployment lists, at most 2 connections, 30 s a statement, 1 MB of masked output. The sysadmin's key on the same account keeps its own mode; the data key opens no log, file or root form. Risks: personal data from rows reaching cards (the instruction says quote only what the work needs), load on production (the limits; the switch below), a secret column the name rule missed (the install prints the hidden columns for review; the deployment's list adds more without a release), text in a row read as an instruction (rows are data) |
| The permission audit is private | Every agent's permission prompt is written, masked and rate-limited, to a file only the base user writes and root reads, through the base channel: never to the system journal that agents read. Older history from before this boundary was moved out of the journal to a root-only archive |
| Repository reads stay reads | Checkouts are refreshed only by a timer under a service user with its own read-only deploy key; the analyst reads them through an ACL grant and a wrapper with a finite set of git forms and options, without a shell, a key or network |
| A worker job never widens its agent | The slot belongs to the agent's own user; the job policy is the specialization's limits intersected with the agent's policy, other agents' pools and sibling slots are denied, one writer per card, and the coordinator's request carries no command, path, model, prompt, settings or limit. The runner re-checks the job against the registry before launch (text hashes, profile, model), the session gets a root-owned settings file and system prompt, the write guard in slot mode allows the slot's working copy and temporary folder only (the files a council's critic reads, `work/inputs/`, are root's and denied to every write), and only the session host, which takes requests from the board's service user alone, starts and stops worker units: no rule lets another user do it. Whatever root writes into a folder of a less privileged user (the patch into the agent's temporary folder, the record into the executor's results folder) goes through directory descriptors that follow no symbolic link, and the slot's instruction placeholders are rewritten root-owned before every job. After the job the working copy, its `.git` included, is the job's writing: the runner reads its head and diff as the agent's user, with no system or global git config, no external diff and no text conversion — root never runs git there, and the job's Edit tool may not write `.git` |
| A diagnostic stays a probe | `kd-diag` reads only the targets of a root-owned catalog: loopback `http://` URLs with an explicit port and no user info, query or fragment, or the name of one of the board's own read-only queries. One GET whose status line is the answer: no redirect is followed, no body is read, the timeout is short. A query is fixed SQL in the board service that never returns a secret column (a push subscription shows its gateway's host, not its endpoint or keys; a notification its title, not its body); the thread keeps only the row count. Only the card's single assignee may ask, only while the card is approved, at most a fixed number of new checks per card per hour, and every result is a message of the card's thread. The caller passes a target name and a card, never a URL, a header or a command |
| Server changes happen only for approved work | The execution executor checks a grant the cabinet wrote from the owner's signed decision: card, assignee, servers, operations, scope hash, status and expiry. On every managed server the exec key is a forced command, `agent-exec-gate`: the executor sends each step as an envelope — the id and the payload of the cabinet's decision (the grant keeps that id inside the signature it stores; its own `decision_id` is only its journal record), the signed plan, the challenge's binding and the owner's passkey assertion — and the gate recomputes the cabinet's challenge, verifies the assertion against a root-owned registry of the owner's signing keys (installed from `kd-cabinet user signers`) and runs only the signed plan's step, on the signed server, with its exact text; a critical action runs once per server, keyed by the signed decision. The grant's own times are not signed, so the gate bounds them by the signed term of the challenge: a plan step runs for at most seven days after the moment the owner signed, a critical action for fifteen minutes, whatever the envelope claims. A factory host that holds the exec key but no signature runs nothing on a server in `enforce` mode; a server in `observe` mode (the rollout mode) logs the failed check and runs the command |
| The gate guards itself, and a plan carries no critical step | Beside the signature the gate applies a policy, `agent-exec-policy` — one stdlib module installed next to it and also run by `kd-admin-propose` and `kd-admin-propose-action`, with the same reason. It holds in both modes and on every way in (a plan step, a critical action, a legacy command), before the signature is read: `observe` tolerates only a signature that does not check out. Rule 1: a command that touches the gate, its settings and once-marks, sudo, SSH, any user's keys or the account commands and files — by path (after quotes, line continuations, `//`, `/./` and `..` are normalized; a glob or variable whose literal prefix starts such a path counts too), by a bare word anywhere, or through an inline interpreter (`python -c`, `perl -e` …), `eval`, a decoder or an archive unpacked into a system root — is refused: the gate and access to a server change only from the owner's machine (`deploy_target.sh`). Rule 2: a plan step, a script or a typed step's formed command, that the critical classifier recognizes is refused: the owner signs it on its own, as an exact command. The site units whose stop is critical come from the overlay's catalog (`deploy_target.sh` writes them into the gate's settings; without them every unit's stop is critical). A refusal is exit 126 and `deny policy (…)` in the server's journal; a policy file that does not load refuses everything but the plan window's snapshot |
| Some actions never happen | The denylist refuses them before execution; an approval does not override it. It reads a command's text: a script step the owner signed runs as written, so treat a signed script as root (or sudo) on its servers — the text is the owner's to read, which is why a packed or encoded payload is refused at proposal. The factory's own host (the inventory's `home`) takes no script step at all — the plan is refused, and the executor refuses it even signed; its catalog operations and exact critical actions stay |
| A project's own step stays the project's | The sysadmin's catalog may name project environments (`apps`): a server, the application's own account (never root) and directory, its interpreter, the tools it may run and the config file with the sections whose switches may be set. Three typed steps work there — on the factory's own host too, because none of them is free text: `app.tool` runs one of those tools with plain-word arguments (a closed character set, no shell), `app.flag` sets one `…_enabled` switch to `0` or `1` through a root-owned helper that rewrites that one line atomically, keeps the day's backup, writes no other key and prints nothing but that switch's old and new value, and `service.reload` reloads a catalog unit. The stage resolves the step into the exact words — `runuser -u <account> -- env -C <directory> …` — and puts them into the plan the owner signs; the target's gate keeps no copy of the catalog and cannot derive them, so it checks three things: the words are the signed plan's; they have the one shape an app step has — an account that exists on that server and is not uid 0 under any name, its directory through `env -C`, then an interpreter and a tool that are plain paths, or the flag helper with one switch; and they pass the same policy as every other step (the stage's denylist reads them before they are sent). The catalog itself is bounded: an entry's account is never root or an account of the platform, its directory lies under an application root (`/var/www`, `/opt`, `/srv`) outside the platform's trees, its interpreter is the system's `python3` or a path inside that directory, its tools are `.py` scripts inside it. A PHP application's entry names the system's `php` by its bare name and the commands of the tree's own `spark` a step may run (the command is the step's first argument; anything else is refused before the plan is signed), and an entry whose switches live in an env file (`.env`) lists the keys a step may set and the values each may take — plain words, never an address, a token or a password; the helper replaces or appends that one line, and prints the old value only when it is a plain word itself. A catalog entry that changed after the signature refuses the step. Free-form SQL and a script on the factory's host stay refused; what a project's tool does to its own database is the project's code, reviewed in its pull request |
| A typed step is narrower than a script | The gate runs a checked typed step as its own words, without a shell; only a script, a critical action and a step `observe` lets through unchecked are text for bash. The routine root changes have typed steps of their own: `package.upgrade` (the system upgrade without a reboot, in a transient unit), `cron.line` (one line of root's crontab, marked with its card), `file.drop` (one file of `/etc/sysctl.d` or `/etc/logrotate.d`) and `gate.script` (below); a root-owned helper on the target does the write, keeps the state before the card's first change in `/root/kd-<n>` and touches nothing else. Their content is narrow so that none is a script under another name: a cron line is one schedule and one command, and that command passes rules 1 and 2 and the stage's denylist like a script; a sysctl file is plain `key = value` lines without the keys whose value is a program the kernel starts (`kernel.core_pattern`, `kernel.modprobe` …) or a pipe; a logrotate file has no script block, no compressor command, no mail and no include. The stage checks it before the owner signs, the target's gate again with its own policy before it runs. `gate.script off` — itself a signed plan step — makes a server refuse every text it would run through bash for a plan (a script step, a legacy command, an unchecked step in `observe`) in both modes, while typed steps and critical actions go on; `gate.script on` returns scripts the same way, so the switch needs no run from the owner's machine. A reboot stays a critical action, signed as its exact command: `system.reboot` forms that command — the helper writes the routing rules, WireGuard, listeners and running services into `/root/<card>/before-reboot-…/` and then reboots; the factory's own host is never its target, and the policy calls the helper's reboot critical in a plan step, so a script cannot reach it. Persistence through a cron line or a unit stays possible within these rules: the owner reads the line he signs |
| Code reaches `main` only with the owner | Forgejo's branch rule requires an Approve on the exact head — the owner's own, or the approver's after it checked his signature; the agent pushes only through a review account and merges through an executor that Forgejo still checks; the executor reads the PR's head and target branch again right before the merge, and a PR that landed in a branch other than the checked one is reported |
| An approval from the cabinet is the owner's | The cabinet holds no code-hosting token. The approver that posts the Approve for him runs under its own user, takes requests only from the cabinet's service user, and checks the passkey assertion itself against a key root registered for that person, one chosen key at a time: the decision, the head, the mode, a term of minutes and a nonce used once (kept on disk, so a restart approves nothing twice). The live pull request must be the developer's, open, into the signed target branch of the project's passport and still at the signed head. A signature carries to a new head only by the approver's own record of what it approved (the head, the mode, the target and the id of the pull request's own diff there, as `git patch-id` reads it: no blob ids, no line numbers): the new head must be the signed one brought up to date with the target and nothing else — down its first parents to the signed head, every commit a merge of two parents whose second is in the target's live head — with the same own diff, uncut, and the passport's required checks green on it. The approver reads all of it from the code host itself; the cabinet only names the pull request and the two heads, and only for a signature that is still approved, into the same target with the same release flag. The Approve on the new head names the decision and the head it came from. A conflict the developer resolved, a commit of his, a cut or unreadable diff, a record older than 30 days — the owner signs the new head |
| A read of a SQLite file stays a read | The read-only gate opens the file itself, with the language's own SQLite module and no `sqlite3` binary: the path passes the same roots and forbidden-path rules as `cat`, the file is opened read-only, and SQLite's authorizer lets through reads only — a write, `ATTACH`, `PRAGMA` or an extension is refused by SQLite, whatever the statement's text; 30 seconds, 1 MB, a 512 MB ceiling on the reading process's memory (one value SQLite builds whole is a refusal, not a server out of memory), the same masking as every other output |
| The developer's dependencies are the lock file's | `kd-deps install` is the one way a developer session installs packages: in a working copy right under its `work/`, `composer install` by `composer.lock` and `npm ci` by `package-lock.json`, with install scripts and composer plugins off, the caches under `work/`, the network the session's exit. The dependency folder must be ignored by git. A package's code runs only when the developer runs the project's tests — in the sandbox that already runs the pull request's own code; `composer`, `npm`, `npx` and `pip` directly stay refused by the hook |
| A candidate's tests run with nothing to reach | A pull request's code runs only in a dev.check's child unit under the ci user: a fresh checkout, no network, no board, session-host or approver socket, no `/etc/digipaddock`, no agent folders, CPU, memory and time limits. The ci user is in no group and has no channel. Its dependencies are prepared before it, by lock hash, by root's runner, so that nothing of the candidate's runs while the network is open: its pip locks may hold plain requirements and hashes only (no index, link, URL or other file) and its npm lock the public registry only; a downloader venv of its own fetches the files and installs none of them, and the venv is installed from them with no index in a unit with no network (npm ci runs with network and no scripts). The one source package and the build backend's lock must be the deployed tree's — a change there is `dependency_update_required`, released first. The root runner itself never runs the candidate's code. The status token can write commit statuses and nothing else, is read only by root, and never enters the unit |
| A release installs only what the owner approved | `kd-release` deploys only `main` (which code reaches only with the owner's Approve) and the overlay's `main`, both scanned. The overlay is data only: the installed release tool checks it before anything runs (an executable or a script in an overlay path refuses the release), the closed scanner is the installed tree's own with the overlay's literal list, and the steps that run code not yet released — the public scanner and the composition — run with the scanners in a sandbox (a dynamic unprivileged user, no network, no home or `/etc/digipaddock`, the input read-only, only its own `/tmp` writable), never as root with the deploy key. It is not code only: after the switch it runs, as root, the new tree's `render_host.sh` (units, the managed rules floor) and `cabinet_setup.sh install` (the cabinet's venv, frontend, units and nginx), and asks the factory to reinstall the roles it would install differently. Approving a PR that touches those installers, units or templates therefore approves what root runs at the next release; the computed cage names every such file on the PR. The reinstall is a factory operation (below), with the modules' own setup scripts; `stage_setup.sh` and a host's first install stay manual |
| A factory operation stays in its catalog | The factory catalog has two operations: `agent.reinstall` of this host's generated agents, and `component.install` of a platform component in one of its fixed modes (each mode one fixed command of the deployed tree). A request carries a card, agent names or a component and a mode, and a key — never a command, path, server or service. A component step's signature names the deployed revision: a later release needs a new signature. The cabinet checks the card's factory grant (the owner's signed plan or approved brief: card, assignee, agents, scope hash, expiry) and the deployed revision; the session host drains the role without killing anything and the root runner calls only the tree's own `new_agent.sh` and checks. The developer's catalog cannot reach servers: those grants are the sysadmin's policy, and an old grant is never read as a factory one |
| Approvals cannot be forged by agents | Grants are written by the cabinet service under its own user, only from a decision a signed-in person signed, where no agent can write; executors read them; a card's status, a comment or a chat message is never a grant. The one grant no person signs is the test zone's (next row): the cabinet writes it itself, by rule, and the record names the rule, never a person |
| A test environment is the agents' working zone, and nothing beyond it | The deployment marks project environments as test in the operation catalog; an environment on the production server cannot carry the mark — the catalog does not load. A plan whose every step is such an environment's own step (a listed tool or spark command, a listed switch and value, a reload of a listed unit) is approved by the cabinet by rule for 24 hours, with no signature: the card's thread and the decision say so, and the owner revokes it like any approval — after his revoke the rule approves nothing more on that card, its next plan is his to decide. Any other step sends the whole plan to the owner. The server decides for itself: `deploy_target.sh` installs there a root-owned list of its test environments, and the exec gate runs an unsigned step only when it fits an entry of that list word for word — the application's account and directory, the tool, the key and value, the unit — after its own policy checks, and logs it as `allow test-env <name>`. The times of an unsigned step are vouched for by nothing, so the gate does not read them: the executor on the agents' host checks that the approval lives, the card is in work and the catalog entry is still marked. A compromised agents' host therefore reaches exactly that list and no further: it can break a test environment, not leave it. The same list opens to the read-only gate's account the directories an entry names under `read` (its journals): `target_setup.sh` sets an ACL on that tree and a default one for what the application writes there later, and takes both off when the list drops them; everything read there still passes the gate's forbidden paths and secret masking |
| Help grants nothing | A lead's help request names a kind from a fixed catalog and a step; it is accepted only from the lead's running turn on its own card in work, and the coordinator may assign only a role of that kind, never the lead. The helper acts with its own policy — help adds no permission, sandbox path or approval, and the step text is data to it. Every kind is a read but `server_change`: there the sysadmin only opens its own card with a plan, which waits for the owner's signature like any other — or, made only of a test environment's steps, is approved by the test zone's rule like any other such plan. A change still needs its own approved plan, and the request ends with the card, its lead or its scope |
| Directives cannot be forged | Directives live in a journal only the base user writes; agents read them through a channel that checks who is asking; a comment that looks like one is just data |
| The owner's word comes only from the cabinet | Agents talk to the owner only in the cabinet: card threads and their own chat. A message counts as the owner's only when the cabinet recorded a signed-in person as its author; an agent's text, a tool's output or a quoted line is data. No agent has a Telegram channel; Telegram carries only the plain-text duplicate of critical alerts |
| Board writes do not race | One service owns the database; every write names the card revision it saw (compare-and-swap) and records its event in the same transaction |
| Agents cannot start work on their own | Board writes go through an executor under the base user (`kd-task`: claim, create, edit, handoff) that checks status transitions; agents keep no direct write access to card files, and the board CLI only reads for them. The executor checks the caller's identity and capability, its right to change that card and field, the status transition and the card revision. Moving a card out of `Inbox` is done only by the cabinet after a person's approval, which names the exact revision (and the brief version) that person saw. Two exceptions: the coordinator starts a subtask under an active delegation grant, and the executor checks the grant, its limits, its expiry and that it was not revoked; and the cabinet moves the sysadmin's own card to `To Do` when it approves that card's plan by the test zone's rule (the row on test environments): the move is recorded as the cabinet's own, names no person, approves no brief and grants nothing — a card that carries a brief is started only by a person |
| The coordinator closes only a stage a review read | The coordinator's one way to `Done` is `stage-pass` on a handed-in stage of a chain plan, and the cabinet checks it against its own records: a ready verdict of every reviewer job the cabinet itself ordered — one per pull request of the plan the stage moved — with every open pull request of the plan on the head it was handed in on (or a hand-in that published nothing new, which nobody had to read), every criterion checked, nothing open on the stage and its agent's turn over. A return names the job of a review with fixes and carries no text of the coordinator, twice a stage at most; the reviewer is a read-only worker job and its findings are data for the stage's agent. The stage's own agent cannot close it past that gate, whatever the project lets it close. A pass accepts neither code nor plan: each of the plan's pull requests reaches its target only with the owner's signed approval after its council, and the plan's acceptance is his. Without a decision in 30 minutes the stage goes to the owner |

## What the owner approves

| Level | Example | Approval |
|---|---|---|
| Read | Server status through the gateway, logs, the board, the docs | none |
| Local work in the sandbox | Tests, local commands, notes | none |
| Start of work | A card from `Inbox` to `To Do` | one click |
| Delegation | The coordinator splits one goal within limits | one click, revocable |
| Server change | A plan for a card: typed steps and scripts whose exact text he reads | once per task, a passkey signature (the servers verify it; a code would not do) |
| Critical server action | One exact command | once per command |
| Monitor trust | An incident's object into the baseline, a server's baseline, a trusted address; a login by a key closed as “access removed” — the monitor closes it only when its latest snapshot, taken after the last login and at most 3 hours old, read every key file of that server and shows none allowing the key, with no keys command, CA or certificate login it could not see — and never puts the key into the baseline | a passkey signature per decision or per bundle; the agent only proposes |
| Code to `main` | A pull request | a passkey signature in the cabinet, or Approve in Forgejo; the code host merges only an approved head. The merge executor reads the mode signed in the cabinet from the Approve's body: a merge takes «approve and merge» or «approve, merge and release», a release only the latter (a merged PR also releases when the owner merged it himself); the owner's own Approve in Forgejo is an admin's word for both. An approved head can be merged later on his word in the thread. A head that only brings the signed one up to date with the target (no conflict, no new commit of the developer, the same own diff) keeps the signature and its mode — no new signature, no new council round; the card's thread says from which head it was carried. A project's passport may ask for a branch current with its target only when a pull request touches named paths (its migrations) |
| Deploy to prod | A project's manual environment (the button on «Deploys»): the branch's head now, `skip_tests` where the workflow takes it | the owner alone: the word `deploy` and a passkey signature **without user verification** (`deploy_prod`, the one such signature), ten minutes, used once; the approver dispatches it only while the branch's head is still the signed commit |
| Forbidden | Denylisted actions, the agents' infrastructure, kill switches | not possible for agents |

A refusal from a classifier or guard is not a reason to ask the owner. The agent fixes the command form or proposes the exact critical action.

## Kill switches

Each switch is one root action on the host and takes effect immediately. Agents know these switches exist but cannot run them.

| Switch | Effect |
|---|---|
| Remove one channel's permission file | That power stops for that agent (for example, server execution, merge, or coordinator writes) |
| Stop the channel target | Every channel of every agent stops at once |
| `host_read_setup.sh off <agent>` | That agent's host reads stop at once, in its running session too, and stay off through reinstalls; `on` returns them |
| Empty the list of enabled servers | No server accepts reads or changes from agents |
| `deploy_target.sh <alias> --exec-mode observe` | That server's exec gate logs an unsigned or mismatched step and runs it (the rollout mode) instead of refusing it; `enforce` returns the refusal |
| Remove `/etc/agent-exec-gate/test-envs.json` on a server | That server's gate asks for the owner's signature on every step again, test environments included; the read directories stay open until the next `deploy_target.sh` run without them (or `target_setup.sh --remove`). For good: take the `test` mark off the catalog entry, release, and run `deploy_target.sh` for that server |
| Remove the envelopes flag file on the factory host | The executors send raw commands again; only servers in `observe` run them, servers in `enforce` refuse |
| Remove an agent's `data` channel file, or the data key's line from `agent-ro`'s `authorized_keys` on a server | That agent's database reads stop (the channel); that server's database stops answering every agent (the key), while the sysadmin's reads there go on |
| Revoke a delegation grant (on its decision in the cabinet) | No new subtasks; directives under it are withdrawn |
| Stop the cabinet service (`systemctl stop digipaddock-cabinet.socket digipaddock-cabinet-http.socket digipaddock-cabinet.service`) | No decision can be given or consumed, the board is neither read nor written and no agent is woken; the data stays |
| `pipeline_setup.sh disable` | The pipeline goes to observe: outcomes, waits and problems are still recorded, no continuation starts; `enable` returns enforce |
| `"chain": false` in `/etc/digipaddock/pipeline.json` | Plans approved from then on are no chain plans: every stage waits for the owner's acceptance again. A chain plan already running stays one; its stages the owner can accept, return or hold himself |
| Disable the release trigger | No automatic deployment |
| `mirror_setup.sh disable` | Nothing is pushed to the public mirror, not even after a release |
| Remove the forge executor's read-only deploy key on the code mirror | `kd-mirror-fetch` fetches nothing more; the mirror never accepted a push from it. The developer's sandbox never reaches the mirror's host and holds no key for it: it reads the branches the executor fetched from a local copy. Dropping `git.mirror` from its manifest and reinstalling takes away `kd-mirror-fetch` and the read grant on that copy |
| `kd-cabinet contour maintenance <name> --reason "…"` (or `devcheck_setup.sh disable` for every contour) | That contour takes no new dev.check; a running one ends; `kd-cabinet contour release <name>` returns it |
| Remove the dev.check status token file | Checks end `environment_not_ready` and write no status: a branch rule that requires the statuses blocks the merge |
| Remove the merge executor from Forgejo's merge allowlist | Merges stop at the code host |
| `review_setup.sh disable` (the approver's socket), or remove the approver from the branch rule's approvals list | No approval from the cabinet reaches the code host; Approve in Forgejo still works |
| `repo_attach_setup.sh disable` | Repository attach requests from the cabinet wait; attached repositories and clones stay |
| `worker_slots.sh --disable` | No worker job is accepted or started; the slot folders stay |
| `transcribe_setup.sh disable` | Voice is not transcribed; recordings stay files |
| `systemctl stop digipaddock-egress@<exit>` (or `egress_setup.sh disable` for every exit) | Requests through that exit fail (with the standing exit: `WebFetch` and commands; `WebSearch` goes on); sessions keep working |
| `new_agent.sh --disable <agent>` | The agent's sessions and channels stop; its data stays; it leaves the session host first |
| `session_host_setup.sh release <agent>` | The agent leaves the session host; its queued commands are cancelled, its running sessions stop, and it does not run until `enable` |
| Remove the Telegram token file | No duplicate of critical alerts; the alerts stay in the cabinet and the system journal |
| `systemctl disable --now digipaddock-alert-watch.timer` | No duplicate of a failed agent session, a denylist refusal on a server or a cabinet that does not answer; unit failures are still duplicated |
| `session_host_setup.sh disable` | No session starts; commands not yet started wait in the board |
| Remove a provider's key file (`/etc/<product>/llm/<kind>.env`), or delete it in Settings → Models with an owner passkey signature | New sessions and worker jobs on that provider's models fail `no_key` with a notice; running processes keep the key until they end. Disabling a model in Settings → Models stops it the same way without touching the key |

A deployment keeps its own runbook of these switches, with its paths and hosts, in its overlay.

## Secrets

- Secrets never enter git, cards, pull requests, comments or memory. They live in files on the host, readable only by the user that needs them.
- Execution keys belong to service users. The agent that requests an action cannot read the key that performs it.
- The dev.check status token belongs to a code-hosting account that may write commit statuses only; root's runner reads it to set `devcheck/<profile>`, and the ci user that runs the tests never sees it. A profile the project's passport marks required is required by the target branch's protection rule too: the merge tool and its self-check refuse while the rule does not require that status, so the code host itself, not only the merge tool, holds a red or missing check back.
- A provider's key (Anthropic API, OpenAI API, OpenRouter, Fireworks, DeepSeek, custom) is a root-only file that systemd hands to the session's process in place of the host's Claude token: the cabinet sees only that the file exists, the sandbox strips the variable from every shell command, the rules floor denies reading the key directory, and the thread's masks cover it. The file is required by the unit, and the host reads it once more right before every start: gone or malformed by then, the session or probe fails `no_key` — a process never starts on the host's Claude login with the provider's endpoint. The model's name, endpoint and effort travel as unit arguments — they are not secrets. Right before `claude` starts, `kd.secret_fd` takes the key out of the environment — `ANTHROPIC_API_KEY` of the Anthropic API and `ANTHROPIC_AUTH_TOKEN` of the other kinds alike — and hands it over a pipe whose write end is already closed (`CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR`: the pinned Claude Code has no descriptor of its own for `ANTHROPIC_AUTH_TOKEN`, and a provider's key works as the API key's); claude reads it once and closes the descriptor, so no key stays in the environment of the agent's own `claude` process.
- Guards refuse commands that mention secret paths, even inside a note or commit message.
- Agents write memory explicitly; transcripts are never ingested.
- The Telegram token is read only by root, for the duplicate of critical alerts: a failed unit, and — read from the cabinet's journal by a root timer — a failed agent session, a server command the denylist refused and a cabinet that does not answer. Executors post their reports to the cabinet under their own users and never read it.

## Accepted residual risks

- **A signed script runs as written.** The denylist and the critical-action classifier read a script's text at proposal; they cannot prove arbitrary shell code safe and are a check, not the boundary. The boundary is the owner's reading: the cabinet shows the script unfolded, the signature covers exactly that text, the server runs exactly that text. Critical actions still need their own approval, and the factory's own host takes no script step: there it would reach the cage itself.
- **The gate's policy reads text, not effects.** Its rules close the known ways a signed plan could rewrite the gate, sudo, SSH or the accounts; two remain. Persistence: a step may install a unit or a cron job that later runs something as root — legitimate plans install units too, so the owner's reading is the boundary there. Indirect writes through variables whose literal prefix is empty (`echo x > $D/$F` with both set earlier in the script) are not recognized, nor is a program that does the write itself (a script file run by path, an interpreter the rules do not list); the bare words and paths it does recognize are the common forms, and the text of a script written in the same step is read like the rest.
- **The signer registry on a target is written from the factory host.** `deploy_target.sh` fetches the owner's signing keys from the cabinet and installs them root-owned on the server, so a factory host compromised at install time could plant a key of its own. The script prints every key it installs (name, user, credential id) for the owner to compare with the cabinet's device list, and a key becomes a signing key only by root's hand on the factory host, one at a time. After the first install a server keeps the keys and the cabinet (rp id, origin) it trusted: a later install with a different set is refused on the server, old and new printed, unless the owner's machine passes `--replace-signers` — the first install is the moment of trust, and a compromised factory host cannot swap the keys afterwards.
- **Workers share their agent's user.** Isolation between worker jobs, and between a job and the agent's own session, comes from separate working copies, the sandbox and the slot-mode write guard, not from separate users. The runner inside the job unit is root: trusted code that prepares the slot and drops to the agent's user before Claude Code starts.
- **Tool output in the cabinet.** A tool's output, up to 4000 characters, is masked by the gateway's secret rules and kept apart from the thread; only people who may steer the agent read it, never another agent. The masks match known forms of secrets (keys, tokens, passwords in URLs, options and name/value pairs); a secret in an unknown form can still show. When the rules cannot be loaded, no output is kept at all.
- **A secret in a readable log.** If a catalog unit or the cabinet's web log ever writes a secret, every agent can read it. Services log failure reasons through the secret masks, and a source is checked before it enters the catalog; the full journal, login and privilege records, the permission audit and signatures are not opened by this risk.
- **The host reader is a trusted boundary.** A new command form or journal source in `kd-host-read` is reviewed like a gateway change; giving an agent `adm` or `systemd-journal`, the system bus or a polkit rule is a change of this model. Current connections, processes and units are visible to every agent; login and sudo history is not.
- **One Claude token runs all agents.** The host's `claude setup-token` token (a year, root-only file, read by systemd and the root worker runner) authenticates every session, worker job and the memory service. It never enters the environment of the agent's `claude` process: the last step before claude (`kd.secret_fd`, run by `agent-launch` and the model probe; the root worker runner does the same itself) moves it into a pipe, closes the pipe's write end and names the read end in `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`; claude reads it once at start and closes the descriptor, so neither claude's `/proc/<pid>/environ` nor its descriptors give it to Claude's own file tools, and the hooks, MCP servers and Bash commands it starts do not inherit it. Bash keeps its own guard as before: the sandbox unsets the credential variables (`sandbox.credentials`) and gives every command its own PID namespace. Without the token file there is neither the variable nor a descriptor. The memory service still reads the token from its unit's environment file. A leaked token works for anyone until it is revoked in the subscription's settings, and revoking it stops every agent at once; a host without the file falls back to each user's own `/login`.
- **A carried signature trusts a merge of the target.** The owner signed his pull request's own change, not the target's commits a later merge brings in: those reached the target through their own approvals. What a merge of the two changes means together — a semantic clash with no git conflict — is not checked before the merge, as it is not for a pull request merged behind its target; the required checks on the new head are the guard where a project has them.
- **The cabinet runs every passkey ceremony.** The approver trusts a fresh assertion of a registered key, not the cabinet's database. It cannot tell which ceremony the person believed he was in: a compromised cabinet service could show a pull request's value as the challenge of a sign-in and get an Approve. Registering for pull requests a key that is used only for signing (not to sign in) narrows this; the code host's own Approve stays available and independent.
- **A prod deploy is signed without user verification.** The owner chose to start a prod deploy from the cabinet with his saved passkey alone, no fingerprint or PIN (`deploy_prod`): an unlocked computer with his signed-in browser is enough to start one. It is bounded: only a manual environment of a project's passport, only the commit at the branch's head the sheet showed (the approver refuses once the branch moves on), the owner's role, the typed word, a term of ten minutes and a nonce spent before the call — a signature starts one deploy. No other decision, sign-in or step-up accepts a signature without user verification, and nothing in it can merge, change code or reach a server. The approver holds the code host's token for it; the cabinet never does. A deploy has no rollback button: what it rolls out is code already on the deployed branch.

## Prepared browser tests

`e2e.request` is a developer capability, separate from a skill. The base executor accepts one registered smoke suite for the caller's approved card and runs a trusted prepared application in bubblewrap with a private network and filesystem, a seccomp filter over the kernel's rarely needed interfaces, and a memory and task bound on the whole call. No production data, credentials, host sockets or caller-selected command/URL enter it. The agent's own sandbox remains unchanged. Preparation is trusted deployment work; absent browser/dependencies or failed namespace setup means blocked, with no unsandboxed fallback. Limits, lifecycle, private artifacts and the exact read-only mounts are documented in [e2e-runtime.md](e2e-runtime.md). Workers do not inherit this channel.

## Provider keys entered in the cabinet

A provider key entered in Settings → Models passes once through the cabinet process's memory on its way to the
root writer. This residual exposure is accepted: a compromised cabinet process can capture a value while the
owner submits it. Python and browser memory are not guaranteed to be zeroed after use. The value is never stored
in SQLite, decisions, transcripts, argv or journals, and neither service permits core dumps. The input is cleared
after an attempt and uses no draft or browser storage. TLS protects the browser leg; the local leg is a Unix socket
restricted to the cabinet UID by both its mode and SO_PEERCRED. Request-body logging must remain disabled.

The root service independently verifies user verification and the passkey assertion against public keys root
explicitly enrolled in its own root-only registry. Neither database edits nor a stolen cabinet session enroll a
signer or authorize a write. A five-minute root-generated challenge binds the owner, provider, action and key digest;
it is consumed before effects and held only in memory. Restarts invalidate every challenge, and an expired or used
signature cannot be replayed. Only catalog provider paths can be written through kd-secret's existing atomic writer
(root:root 0600), or unlinked. The service has no key-read operation and no network. Revocation by root is checked
on every operation. As with PR signatures, a compromised cabinet can misrepresent what ceremony it presents to the
owner: a separate signing passkey narrows this risk. The root signer enrollment is trusted administrative work.
The [runbook](model-provider-keys.md) covers enrollment, revocation, the socket switch and partial audit failure.

### Subscription and direct APIs

The signed root protocol additionally accepts the fixed subscription target `claude-subscription` (replacement only),
and catalog targets `anthropic` and `openai`. Subscription deletion is refused before any effect. The subscription
uses the existing format validator and secret writer; only the catalog's fixed Hindsight units are restarted.
Restart failure is distinct from write failure. Status returns metadata, not the credential. Estimated age and expiry
come from file metadata and are not cryptographic claims about the token's actual lifetime.

Atomic replacement of the subscription file requires write access to `/etc/digipaddock` in the key service's mount
namespace. The root-enrolled signer registry has an explicit read-only mount to retain its separate enrollment
boundary. The browser cannot choose a file, environment variable, command or restart unit.

The OpenAI adapter has no tool executor and no board socket access. It runs as root to read the root-only provider
file, with an empty capability set, read-only filesystem, protected home, disabled core dumps and a loopback listener.
Every generation/count request authenticates with the current provider key; anonymous callers cannot spend API
credit. It forwards only to fixed OpenAI HTTPS endpoints without redirects and never logs bodies, headers, reasoning,
credential values or upstream error text. The fixed inference transport grants no new power to an agent's tools.
Native Anthropic API credentials join the fail-closed Bash environment deny list (policy schema 7).
