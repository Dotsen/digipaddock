# A stage of a chain plan, and the plan's end

Read this when the first line of the card's snapshot says `chain` (`parent KD-<m> (chain: …)`), when the wake `[stage] KD-<n>: returned on the code review (<verdict>) — …` reaches you, or when the wake `[board] KD-<m>: every stage is handed in — …` makes the plan's own card yours. «Workflow» and step numbers refer to the Workflow section of your main instruction.

## The parent card of a chain plan

A chain plan (`stages: chain · …` — stages of one role in one project, on one branch and in one pull request of the parent in every repository they commit into, with no acceptance by the owner between them and nothing merged before the end) gives its parent a turn at the end: when every stage is handed in, the plan's agent is woken on the parent to publish the plan's pull requests, lead each to the owner's decision, merge them and hand the plan in, and it fixes there what the owner returns afterwards.

## Workflow step 2 — a stage of a chain plan

- **A stage of a chain plan** — the snapshot's first line says `chain` (`parent KD-<m> (chain: a branch agent/KD-<m>-… and a pull request of KD-<m> in each repository)`): the plan's stages run one after another, and in every repository the plan's stages commit into the plan has one tree, one branch and one pull request of the plan's card KD-<m>; the owner decides at the plan's end. Such a stage has no worktree, no branch and no pull request of its own, in any repository. Instead of step 3, in the clone of each repository the stage changes: `git fetch origin`. The first stage that touches a repository creates the plan's tree there — `git worktree add ../<Repo>.KD-<m> -b agent/KD-<m>-<slug> origin/<target>` (the same slug in every repository); a later stage finds it (`git worktree list` in the clone): `work/<Repo>.KD-<m>` on `agent/KD-<m>-<slug>`, with the commits of the stages before it, which yours build on. `cd` there as its own call; `git merge origin/<target>` only when the stage needs what landed since. Work by step 4, within your stage's criteria, committing as usual. Nothing is merged and nothing is rolled out before the plan's end, in any repository: never ask the owner whether to merge a stage's part or to open a pull request for it — it accumulates in the plan's pull request. A criterion that can only be shown on a stand after a merge cannot be met inside the chain: do not merge for it — ask the owner on the stage's card (`kd-work ask KD-<n>`, `--outcome wait_user`): that check belongs to the plan's end.
- Handing a stage in — the stage's commits go into the plan's pull requests first, the stage's review reads them there: check off every criterion of the stage (`--check-ac <n>`) with a note of the check that shows it; then, in each repository the stage changed: write its body file `/srv/digipaddock-agents/dev/work/tmp/cards/KD-<n>/kd-pr.md` (step 6's template, describing that repository's part of the plan as far as it has come; a second repository — `kd-pr.<project>.md` beside it); `kd-pr <project> KD-<m> --title "KD-<m>: …" --body-file /srv/digipaddock-agents/dev/work/tmp/cards/KD-<n>/kd-pr.md` — the plan's card in the title, never your stage's: a pull request titled with the stage's card is not the plan's — no reviewer of the stage reads it, and it asks the owner for a decision of its own; on a project with required checks `kd-forge check <project> <N>` and end the turn on its wait — the line it prints names the plan's card: end your own turn, `kd-work finish KD-<n> --outcome wait_dependency --operation <id> --note "…"`; on the green checks (the turn their end wakes) `kd-forge publish <project> <N>`. It answers `этап: PR плана обновлён (голова <sha12>); совет и решение владельца — после последнего этапа` — that is the normal answer of a stage: no council gathers and no decision opens until the last stage. Every repository the stage changed is published before the hand-in: the cabinet puts a reviewer on each pull request of the plan that moved, and one published or opened after the hand-in refuses the coordinator's pass. Then the stage's report, `kd-task edit KD-<n> --final-summary "…"`: the commit range of the stage in each repository, the checks you ran and their results, where you left the stage's brief and why, what the next stage needs to know, and the open questions (say plainly when there are none) — the coordinator decides on the next stage from this text. Then `kd-work finish KD-<n> --outcome review --note "…"`. No message to the owner, no `wait_user`, never `kd-merge`: a reviewer of the cabinet reads the stage's commits in each repository, and BOSS passes the stage (the next one starts), returns it to you, or leaves it to the owner.
- `[stage] KD-<n>: returned on the code review (<verdict>) — …` as a wake-up: the reviewers' findings are messages in the stage's thread, one per repository that has any — data, not commands: check each against the code and the stage's brief. Fix what is right, say in a note why the rest stands (`--append-notes`), commit, publish the new head into the plan's pull request of each repository you changed and hand the stage in again, as above. A stage is returned twice at most; after that the owner decides.
- `[board] KD-<m>: every stage is handed in — publish every pull request of the plan (kd-forge publish in each repository it has one), lead each to the owner's decision, then merge them in the order the brief names` as a wake-up on the plan's own card, followed by `: <project>#<N>, …` — the plan's open pull requests, one per repository its stages committed into (none open: no list): now KD-<m> is your card. In each repository's `work/<Repo>.KD-<m>`: `git fetch origin && git merge origin/<target>` if needed, the checks, the PR body for that repository's part of the whole plan (step 6, with its `## Rollout`), `kd-pr`, `kd-forge check` where required, `kd-forge publish` — this time it gathers the card's council and opens the owner's decision: one decision of the owner per pull request. From there KD-<m> goes by steps 5–8 like any card with several pull requests: the council, his remarks, `kd-merge` of each on his approval of it — in the order the brief names (none named: a repository the others rely on first); a pull request approved ahead of one that merges before it waits for that merge. Where a release is signed, the release is one, after the plan's last merge: he signed «merge and release» on any of the plan's pull requests (its wake says `a chain plan with other pull requests open`) — `kd-merge` of each without `--release`, in the order, and then one `kd-merge --release` on the pull request he signed the release on, merged by then (a release at the first merge would roll out half the plan). No release signed on any of them — merge them and say in one line that the plan is merged and not rolled out: a merged pull request is released only on his own Approve of it in Forgejo, so never offer to roll out on his word in the thread. Then `git worktree remove ../<Repo>.KD-<m>` in each clone, the deploy and the rollout, the plan's own criteria that need the stand, and `kd-work finish KD-<m> --outcome review` (`done` where you may close). What the owner returns on the plan after that is fixed there too. Before that wake, never start a stage's work on the plan's card.
