# The monitor: a fixed problem's recheck, a plan step's window, a login whose access is gone

Read this before you run `kd-monitor fixed` or propose `kd-monitor revoke`, and when a notice or an incident follows a plan step.

## After you fixed a monitor problem

Mark it only when `ssh-ro` shows that the checked value itself is back to normal (not just that the cause is gone); for `mem` (PSI avg300, swap over 5 min) wait ~10 minutes after the fix. The monitor rechecks the problem on its next tick, even a daily check: one good result closes it («закрыта»), a bad one comes back as «P-<n> исправление не помогло». If `fixed` answers that the problem is already closed, close the card right away: the final summary, then `--outcome done`. Run `fixed` again only after a new fix, never just to get another recheck.

## A plan step keeps the baseline itself

Each step of an approved plan (`kd-admin-run`) and an approved critical command (`kd-admin-critical`) runs inside a plan window that the executor opens and closes: meanwhile the monitor does not compare that server's snapshot, listeners and WireGuard peers, then takes what the step changed into the baseline — no incidents, and one notice in the card's thread («… — в эталон N»). It takes only the objects the step's kind may change: a script and a critical action any; `package.install`/`package.upgrade` users, cron files, units and listeners; `service.start`/`restart`/`reload` listeners and WireGuard peers; `cron.line` root's crontab. Anything else that changed meanwhile is checked as usual. A step of the test zone (no owner's signature) and a kind that changes nothing the monitor watches (`app.*`, `file.drop`, `gate.script`, `package.refresh`) open no window. A dangerous change (SSH keys, sudoers, groups, a uid 0 user, a weaker sshd, `ld.so.preload`, a firewall turned off) and an object that already differed from the baseline before the step still open their incidents, linked to the card: explain them to the owner in that thread and, if they are the step's intended result, propose their accept (`kd-monitor accept … --text`). You never open or close a window yourself; a step whose window did not open (the notice «окно шага плана … не открыто») is checked as usual.

## A login whose access is already gone

Never propose `accept` for it — that would trust the removed key. `kd-monitor revoke P-<n> [P-m … | P-a..P-b] [--text "<how the access was removed>"]` opens the owner's decision «доступ снят» (only for a login by a key: not `gap`, not `@password`/`@key ?`) and changes nothing. After he signs, the monitor checks its latest snapshot of that server: the key still in any `authorized_keys` — the decision ends «ошибка: ключ ещё разрешён на …» and the P-n stays open; the same when the snapshot cannot prove it gone (taken before the last login or over 3 h old, a key file it could not read — a symlink, too big —, sshd with a keys command, a CA or an `AuthorizedKeysFile` outside the homes, a login by a certificate); gone — the P-n closes as «доступ снят», the key is not put into the baseline, and its next login opens a new problem. Before proposing, confirm with `kd-monitor keys <fingerprint>` that the key is no longer allowed there. The same rule as accept: only on the owner's message in the cabinet.
