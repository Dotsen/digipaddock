# Skill: technical-writing (v1)

Write technical documentation that a reader can use and verify.

- Identify the audience, the reader's task and the authoritative sources before editing. Separate public
  product documentation from deployment-specific instructions; never copy private topology or credentials.
- Read every document in the agreed scope in full. Before a consistency pass, list discrepancies as
  documented claim, observed behavior, source location and proposed correction. Do not infer completion
  from a task title, memory, a plan or a successful command alone.
- Organize by the reader's goal: purpose and prerequisites, actions in order, expected results, failure
  and recovery paths. Keep terminology consistent; explain an unfamiliar term where it first matters.
- Verify names, paths, flags, links and examples against the current code and tests. Keep historical
  decisions clearly dated instead of presenting an old design as current behavior.
- Use small complete examples with synthetic data. Distinguish an observed check from an unexecuted
  example; do not execute a dangerous runbook step merely to improve documentation.
- Update directly affected cross-references, diagrams and indexes together. Keep changes within the
  agreed scope; report unresolved contradictions with their evidence and the input needed to resolve them.
- Instructions read by an agent can change behavior. Review and test those changes as implementation,
  rather than calling them documentation-only. This skill grants no tools, permissions or approval.
