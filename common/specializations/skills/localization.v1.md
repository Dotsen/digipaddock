# Skill: localization (v1)

- Establish the project's actual languages, catalog format, interpolation implementation and approved terminology before editing. The cabinet currently uses flat ru/en JSON catalogs and simple `{name}` interpolation in `i18n.svelte.ts`; it does not implement ICU plurals. A schema URL is not evidence that ICU expressions work.
- Keep every supported catalog in step. Preserve key names, parameter names and types; a translator may reorder placeholders but must not lose or rename them. Run the existing catalog tests and `python scripts/check_localization.py` for this repository. Do not interpret catalog text as markup or commands.
- Translate meaning and audience intent, including error guidance and next actions. Preserve product facts, commands, identifiers and protocol values. Cite the maintained source of a claim; do not improve the apparent translation by inventing features, prices or promises.
- Use the project's glossary or approved examples for recurring words. If none exists, propose a small glossary with source references and label it as a proposal. Do not turn an inferred term into an approved product decision.
- For quantities test representative values (0, 1, 2, 5, 11, 21 in Russian where appropriate). Use supported pluralization or a deliberately neutral phrase; never insert an unsupported ICU expression. Dates, numbers, time zones, units and currency follow the project's locale-aware formatter and explicit product requirements, not server defaults.
- Verify long translated strings, narrow screens, wrapping, controls, empty/loading/error states and long names. Check an actual rendered screen where authorized. A key/placeholder check cannot establish semantic accuracy, plural correctness, accessibility or absence of overflow.
- Keep all user-visible strings in the established message mechanism; update every supported language. Internal keys, logs and technical identifiers stay stable. Never include secrets or real customer data in examples or screenshots.
- Report languages, changed keys/files, glossary sources, commands and checks performed through the specialization's existing result. Explicitly list missing context and checks not run. If the browser or test origin is unavailable, state that limitation; do not count unit tests as a visual check or widen access.
